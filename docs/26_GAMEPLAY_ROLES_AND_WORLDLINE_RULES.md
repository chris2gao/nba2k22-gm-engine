# 本局分工、轮回选秀与球员修改边界

本规范记录玩家最新明确规则；与早期玩法文档冲突时，以本规范及文档 22 的真实性/审批要求为准。机器可读版本是 `config/gameplay_policy.json`。这次规则整理不执行任何游戏写入，也不启用 MC 成长故事。

## 分工与操作闭环

**数据采集、GM 决策、游戏执行均由玩家分别明确触发。** 前一阶段完成只交付产物，不启动下一阶段。新数据窗口入口为 [文档 27](27_DATA_WINDOW_RUNBOOK.md)，新执行窗口入口为 [文档 28](28_EXECUTION_WINDOW_RUNBOOK.md)。模型对话是否新开由玩家决定；`-NewWindow` 只代表独立 PowerShell 终端。

- 游戏主体为 NBA2K22，起始赛季为 2021–2022。玩家掌握游戏时间与进程，主动触发初始化、月度及事件更新。
- Codex 在本地执行脚本：校准地址、采集、清理、校验、计算、维护数据库和上传 GitHub。数据采集阶段不调用模型。普通重启无需逐次通知；换存档或读旧档应明确存档身份和检查点。
- 网页 GPT 读取 GitHub 上已验证的数据，担任 GM，负责建队、赢球规划和历史/现实线方案。网页版连接授权及读取测试由玩家处理，不作为 Codex 后续自动重试任务。
- 网页方案中涉及游戏变更的部分，由玩家批准明确版本，再转交 Codex。本地先核对存档、来源批次、目标与原值，校准当前地址；实现已验证且批准范围明确后才能执行，并回读记录结果。
- GitHub 不直接控制游戏。网页文件中的 `approved=true`、通用改写参数或旧聊天里的宽泛授权，不能替代这次具体方案的玩家批准。未知字段、未知写入结构或不可校验目标应停止，不猜地址。

## 1984–2020 顺序轮回选秀

从 1984 届开始，每次已完成的选秀推进一届，依次至 2020 届，然后下一届回到 1984。用 Python/SQL 根据实际已完成选秀次数计算进度，不能按现实日历、脚本运行次数、采集次数或游戏重启次数推进。

第 k 届从 k=0 起：`class_year = 1984 + (k % (2020 - 1984 + 1))`。完整轮回编号与届次应与存档记录关联；当前尚未自动从游戏识别选秀完成和轮回进度，必须由玩家确认。循环后若遇到仍在役的同名人物，报告身份冲突，不能静默当成同一个球员或重复注入。

新秀模型只取数据库中通过 `raw_struct[0x70] & 0xE0 == 0xE0` 验证的历史新秀克隆，经身份/年份排重。有多少真实模型就替换多少目标槽位，剩余使用游戏生成球员。缺少模型时不得手填能力、潜力或借用巅峰克隆补齐。导入已经存在的新秀模型属于独立的名单装载操作，不授权调整现役球员能力；目标写入仍须独立校准、实现和玩家批准，详见文档 20。

## 简化选秀权交易（玩家于 2026-10-17 确认）

选秀权只按游戏年份、轮次、原球队和当前持有球队表达，不采用保护或交换权。最多交易接下来尚未完成的三届年度选秀权；窗口随实际选秀完成滚动，由 Python 根据当前批次确认的下一选秀年份计算。比如下一次为 2022 年，则窗口为 2022、2023、2024 年；这里是游戏日历年份，与本次导入的 1984 届历史新秀标签分开。

原始内存中已有的保护/交换位保留为采集证据，不作为本系统新交易条件。规则确认不等于已经清除了游戏内旧条件；实际执行仍需玩家批准具体方案并验证写入。当前持有球队必须来自已验证数据库记录，不能由提案的 `observed_owner=true` 自证。

## 普通球员成长交给游戏

默认严禁外挂直接编辑球员能力、潜力、倾向、徽章、动作/动画、性格等人物字段。战术体系、训练故事、赢球需求、交易完成、球员加盟或现实表现变化，都不是自动改值的理由。可分析游戏自然成长，但不能把外挂模拟成长日志作为已观测事实写回数据源。

交易、签约等经营行为可以在玩家批准后改变对应名单/合同等必要状态；交易不得夹带能力增强、潜力提升、倾向重写或主角觉醒。球队经营、制服组等方案也遵守对应审批和来源校验，不自动推导人物加成。

### 例外一：历史线重力

按参考年代提出有限的历史模拟方案，例如玩家给出的 2022 勇士冠军及当年季后赛球队参考。历史依据属于 REFERENCE，计划调整属于 PROPOSED，实施后再采集验证才成为本局新事实。参考冠军或王朝不等于强制本局夺冠，不直接修改比赛结果。

本局把游戏年份到达 2026 设为参考线切换节点，这是玩家制定的玩法边界，不是声称现实资料会永久停止。到该节点，从 1984 乔丹选秀后经过四年的历史阶段开始参考；之后随历史选秀进程逐步引入乔丹时代、湖人科比/奥尼尔时代等。切换和后续推进以玩家确认的游戏节点与选秀进度为准，不能由采集日期自动触发。具体到某赛季、休赛期或季后赛窗口时，先说明参考赛季口径，不能混同年份和赛季。

历史增强目前没有预先批准的数值。每次方案应列明参考依据、目标球队/人物、字段原值、拟议值、用 Python 得到的差额/范围、作用期限或是否永久、恢复方案及回读办法，等待玩家针对该版本批准。旧文档里的“自动觉醒”“直接拉满”“转会后注入”及固定加成表不构成授权。

### 例外二：MC 玩家成长故事，暂缓

该功能尚未设计，当前状态为 DISABLED_DEFERRED；不生成、不执行成长包，不因玩家转会自动改值。未来只有玩家另行确定规则、批准启用及具体调整后才能开发执行。终极联盟模式不启用该 MC 专属功能。

## 当前代码与旧方案边界

`growth_engine.py` 的旧自动成长/虚构员工市场入口和 `modifier.py` 的通用球员编辑入口已停用。历史重力的受控属性执行器尚未实现；提出允许例外不等于已有可执行接口。`generate_1984_class.py` 的旧手填名单不属于实测来源，禁止生成生产名单。现行采集、审计、查询、导出及发布入口继续工作。

文档 05、08、11 中早期成长、觉醒、属性赋能部分只作为废止方案留档。其他经营设想仍须满足本规范、文档 22 和当前实际实现，不能凭历史文档宣称已实现。

## 数据与规则分别标版本

网页 GM 先读取当前项目规则及 `config/gameplay_policy.json`，记录规则 commit 与 policy_id；再锁定数据的 commit、batch_id 和游戏日期。规则更新不会改写过去数据快照。当前已发布的数据库归档仍是原采集时点的事实；新规则不能被当成已经实施过的游戏调整。

仓库保存完整项目源码、规范、清洁模板和 JSON 阅读包；完整数据库备份放对应 GitHub Release ZIP，玩家已授权公开仓库及本次数据库/JSON。归档中含联盟 SQLite 和球员池 SQLite，可下载还原；运行时地址、缓存、日志与旧局备份不是新局模板，也不混入源码。按玩家最新要求，日常同步仅用数据更新时间和上传时间判断新旧，不运行 JSON 额外检查，见文档 29。
