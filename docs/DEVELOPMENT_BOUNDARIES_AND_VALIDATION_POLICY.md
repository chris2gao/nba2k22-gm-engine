# 开发规范：边界优先、实现优先、范围内验证

版本：`PLAYER_DEVELOPMENT_POLICY_V1`。玩家于2026-10-18在DEV-10 V2/M0开发中明确确认；适用于后续Codex开发任务。本文记录工程取舍，不授予任何具体游戏写入、采集、发布或经营批准。

## 玩家确认的开发方式

**先定好合理边界，在边界内做最好的实现，只完成适量、直接相关的验证。主要精力投入优秀实现；边界不宜过严，不能让检查和测试挤占实现。**

1. 开始任务明确本次输入、输出、可改模块、禁止动作和交付条件。已有边界清楚时直接实现，不把常规可逆选择反复交给玩家批准。
2. 验证只覆盖本次改动直接相关、能够说明关键业务路径与边界成立的最小集合。复用已验证机制，不重复证明与本次无关的字段、菜单、存档重启、比赛效果或整套历史测试。
3. 不追求“消灭所有可能错误后才能交付”。允许存在**开发时尚未发现、当时被认为正确的bug**，不只是已经登记并标UNKNOWN的风险。不能要求开发者预先识别每一种隐患，再为其增加防线、检查或验收门槛。后续使用或开发发现问题后再检查修复即可。
4. 玩家举例：现金有符号值被按无符号读取，开发时通常不会主动发现，反而会以为正确，直到使用中出现数十亿资金。即使这种bug影响较大，也属于玩家接受的研发取舍；**实现才是开发阶段的主要问题**。本例不要求当前任务追加现金调查、测试或修复，也不把它变成其它模块必须预防的检查清单。
5. 对本次尚不能确认的语义，保留原始事实，明确UNKNOWN/假设与已知限制；以后按实际问题修正。不得为了让报告通过而修造历史数据，或把猜测标为已验证。
6. 完成边界内实现和必要验证即可交付，说明已经做过什么、未做什么、已知问题与下一步；不自动把剩余风险转换为新任务或新的验收前置条件。后续修复由玩家实际需求触发。

## 必须继续遵守的边界

- 阶段仍由玩家分别触发；开发不自动进入正式GM、生产采集、数据发布或游戏执行。
- 玩家批准范围、事实/派生隔离等关键行为边界保持清楚，已有只读/身份/共享位保护直接复用。功能细节的边界不要越设越严；不把“边界”扩张成对所有数据正确性和边缘情形的穷尽保证。测试精简不扩大游戏写入授权。
- 已明确要求的特定验证按本次任务完成；新增广泛验证不是默认工作。玩家可在任务中明确延后某项验证，按最新指令记录，不冒称其通过。
- 同一失败仍遵守三次修复预算；只读诊断不算修复。测试是定位本次问题的工具，不是无限扩大范围的理由。

## DEV-10 M0的具体应用

本轮只实现静态双库只读查询、有限结果/聚合、字段证据和操作手册。合成隔离测试、现有M02副本CLI检查及直接受影响的导出钩子测试构成范围内验证；不运行全项目测试、采集、比赛、保存/重启、游戏写入或Web三窗口连接试验。

玩家已明确将三个Web模型的真实连接留到工程完成后建立，有问题届时修复。cash原始uint32保留，signed32仅列为假设；不为了本轮交付追做原生UI/签约资金机制调研，不启动M1—M4。
